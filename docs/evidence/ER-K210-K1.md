# ER-CAM-steps K1 — OV2640 colour bars through the DVP into SRAM

Sensor: **OV2640 at SCCB 0x30** (PID 0x26, VER 0x42; [[ER-K210-M3]] §2).

## Status when the step plan arrived

- **M0–M4 already done** (uncommitted, review pending). M0/M1 accepted by verify (`docs/verification/ER-CAM-BATCH-1.md`). M3 ([[ER-K210-M3]]): sensor id, camera API, frame format v1. M4 ([[ER-K210-M4]]): QVGA RGB565 and Y8 room images over UART at 1.5 Mbaud, ~1% chunk loss with pacing.
- **What `dvpdiag` showed** (the temporary M4 diagnostic, since deleted):
  - First, frames completed (`sts` frame start/finish, 63 ms per frame) but every byte of the buffer was 0; with the colour bar on as well.
  - `SYSCTL.POWER_SEL = 0x00000000`, `MISC = 0x00000100`.
  - Setting `MISC.SPI_DVP_DATA_ENABLE` (DVP data pins = SPI0 D0–D7) gave real pixels (`zeros=423 sum=3875252`). That fix is in `dvpInit`.
- **K1 isn't new ground** after M4, but it is the first check against a *known* pattern with exact bytes, so it is done here as specified.

## Check (written before the run)

With the OV2640 colour-bar pattern on (COM7 bit 1), one QQVGA (160×120) RGB565 frame captured by the DVP into an SRAM buffer and dumped as hex over UART at 115200 shows:
1. eight vertical bars, 20 px wide each: within each bar, the pixels of a row vary little (min/max of the 5 most significant bits of R, G, B within ±2 levels), and rows 10, 60 and 110 give the same per-bar values;
2. bar colours in the OV2640's order, left to right: white, yellow, cyan, green, magenta, red, blue, black (expected RGB565 near FFFF, FFE0, 07FF, 07E0, F81F, F800, 001F, 0000 before the DSP's colour processing).

Pass = 1 and 2 hold. Exact hex values are recorded either way.

## Attempt 1 — result: **fail on check 1, pass on check 2**

`drivers/unitv/examples/colorbar` (9,696 B code), flashed with `tmp/k210/flash.sh`, read with `capture.py 8`; log `tmp/k210/logs/k1-colorbar.log`. Per bar: centre pixel hex, then `[r min-max g min-max b min-max]` over all 20 px of the bar (5/6/5-bit levels).

```
colorbar: sensor OV2640 addr 0x30 pid 38 ver 66        (= 0x26 / 0x42)
colorbar: frame 2 160 x 120
row 10:  DEBB[r26-27 g52-55 b19-27] D720[r25-27 g56-58 b0-0] 071F[r0-0 g56-63 b10-31] 07E0[r0-0 g63-63 b0-9] F01F[r13-30 g0-39 b0-31] E800[r28-30 g0-0 b0-31] 081F[r1-24 g0-3 b0-31] 1062[r1-2 g0-4 b1-31]
row 60:  D6DB[r25-27 g52-55 b20-27] D720[r25-26 g57-58 b0-0] 073F[r0-0 g56-63 b10-31] 07E0[r0-0 g63-63 b0-10] F01F[r13-30 g0-40 b0-31] E800[r28-30 g0-0 b0-31] 081F[r0-24 g0-3 b0-31] 1082[r1-2 g0-4 b1-31]
row 110: D6DA[r26-27 g52-55 b21-27] D720[r25-27 g57-58 b0-0] 071F[r0-0 g56-63 b10-31] 07E0[r0-0 g63-63 b0-10] F01F[r13-30 g0-40 b0-31] E800[r29-30 g0-0 b0-31] 081F[r1-24 g0-3 b0-31] 1082[r1-2 g0-4 b1-31]
row 60 first 16 px: DEFB DEFB DEFA DEFB DEDB DEDB D6BB D6DB D6BA D6DB D6DB D6BB D6DB D6BA D69B D69B
```

- **Check 2 — pass.** Centre pixels, left to right: white-ish D6DB, yellow D720, cyan 071F, green 07E0, magenta F01F, red E800, blue 081F, black 1082. That is the OV2640 bar order; values are slightly below full scale after the DSP. Rows 10/60/110 agree to ±1 level (frames 2 and 3). Frame 1 (the first after `Open`) was brighter (FFFF, FFE4, …), before exposure/gain settled.
- **Check 1 — fail as written.** Several bars span a channel's full range over their 20 px (magenta `b0-31`, blue `r1-24`). The extremes are at the bar edges, where the DSP's scaler blends neighbouring bars. The window counted every pixel of the bar, edges included. The rows themselves are consistent across the frame.

## Attempt 2 — check (written before the run)

Same capture. Per bar, min/max over the **interior** pixels only (x from bar·20+4 to bar·20+15, 12 px, dropping 4 px at each edge). Pass = in every bar and each of rows 10/60/110, each channel's interior span ≤ 3 levels, plus check 2 as before.

## Attempt 2 — result: **pass**

Same firmware with the interior window; log `tmp/k210/logs/k1-colorbar-2.log`:

```
colorbar: frame 3 160 x 120
row 10:  D6BB[r26-27 g52-54 b26-27] D720[r25-26 g56-58 b0-0] 071F[r0-0 g56-58 b31-31] 07E0[r0-0 g63-63 b0-0] F01F[r30-30 g0-0 b31-31] E800[r28-29 g0-0 b0-0] 081F[r1-1 g0-0 b30-31] 1082[r1-2 g3-4 b1-2]
row 60:  D6BB[r26-27 g52-54 b26-27] D720[r25-26 g57-58 b0-0] 073F[r0-0 g56-57 b31-31] 07E0[r0-0 g63-63 b0-0] F01F[r30-30 g0-0 b31-31] E800[r29-29 g0-0 b0-0] 081F[r1-1 g0-0 b30-31] 1081[r2-2 g3-4 b1-2]
row 110: D6BB[r26-27 g52-55 b26-27] D720[r25-26 g57-58 b0-0] 073F[r0-0 g56-57 b31-31] 07E0[r0-0 g63-63 b0-0] F01F[r30-30 g0-0 b31-31] E800[r29-29 g0-0 b0-0] 081F[r1-1 g0-0 b30-31] 1082[r2-2 g3-4 b1-2]
```

- **Interior spans:** largest is 3 levels (white's G 52–55, row 110). All others are ≤ 2, in frames 1, 2 and 3 and in rows 10/60/110 → check 1 passes.
- **Bar order:** white, yellow, cyan, green, magenta, red, blue, black, the same in every row → check 2 passes.
- **Conclusion:** the OV2640 → DVP → SRAM path delivers the sensor's pattern as RGB565 with correct pixel order (the halfword fix from [[ER-K210-M4]] §3 is in `Capture`), at the expected positions, stable across rows.
