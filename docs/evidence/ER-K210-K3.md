# ER-CAM-steps K3 — camframe decodes esp32cam's ERIM v1 stream

Input (read-only, esp32cam's E3 run): `~/src/tmp/esp32cam/final/stream.bin`, 773,210 B, SHA-256 `d0e328463e003d689f0cb0381ec3dffc54f4132a35a1b829162c1651fd6486bd`; esp32cam's own PNGs `final/0.png … 4.png`.

## Check (written before the run)

`camframe -in stream.bin -n 0 -out <scratch>`:
1. 5 images, `crc_errors=0 dropped=0 lost=0`;
2. each PNG equals esp32cam's PNG of the same seq pixel for pixel. Where it doesn't, the per-channel difference is quantified and explained by the YUV→RGB conversion each tool uses.

Pass = 1 and (2 equal, or 2 explained).

## Result: **pass** (decode identical; pixels within ±1 LSB, difference explained)

```
camframe -in ~/src/tmp/esp32cam/final/stream.bin -n 0 -out tmp/k210/k3
saved k3/0.png 320x240 YUYV sensor=OV3660 ts=6043491 bytes=153600
… 1.png ts=6403671 · 2.png ts=6763850 · 3.png ts=7124031 · 4.png ts=7484210
images=5 saved=5 fps=99.52 crc_errors=0 dropped=0 lost=0 text_bytes=570
```

- **Check 1: pass.** 5 images, 0 CRC errors, 0 dropped, 0 lost. The 570 text bytes are esp32cam's firmware log lines (`grab: …`), passed through as `dev|` lines. camframe agrees with esp32cam's own tool (`camgrab.log`: "images 5, crc errors 0, dropped 0, lost 0").
- **Device timing:** the device timestamps show 360 ms per image.
- **fps line meaningless here:** with `-in` it measures decode speed on the Mac (99.52), not the camera; a later camframe fix can take fps from the device timestamps for file input.
- **Check 2: not identical, explained.**

| seq | Identical pixels | Max \|Δ\| per channel (R, G, B) | Mean Δ (camframe − esp32cam) (R, G, B) |
|---|---|---|---|
| 0 | 12.63 % | 1, 1, 1 | +0.510, −0.459, +0.482 |
| 1 | 13.14 % | 1, 1, 1 | +0.503, −0.461, +0.481 |
| 2 | 12.96 % | 1, 1, 1 | +0.507, −0.458, +0.485 |
| 3 | 12.90 % | 1, 1, 1 | +0.514, −0.465, +0.471 |
| 4 | 13.09 % | 1, 1, 1 | +0.511, −0.456, +0.486 |

All pixels of all five images are within ±1 in every channel. Both tools use BT.601 full-range YUV→RGB with the same fixed-point coefficients (91881, 22554, 46802, 116130 / 2¹⁶); they round differently:
- esp32cam's `camgrab` (`tmp/esp32cam/host/camgrab/main.go:235`): `c + (91881·e)>>16` etc. The product is shifted alone, so it is floored and Y is added unscaled.
- camframe uses Go's `color.YCbCrToRGB` (`cmd/camframe/convert.go:74`). Y is scaled by 0x10101 before the coefficients are added, and the whole sum is shifted, which adds up to ~1 LSB.

That gives camframe ≈ +0.5 LSB on R and B and −0.5 on G on average, the pattern above. Neither is wrong for an 8-bit PNG. If both tools must produce identical bytes, one should call the other's function; I recommend camframe's (the standard library's) for both.
