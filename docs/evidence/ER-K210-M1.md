# ER-K210 M1 — flashing path and UART hello on the UnitV

**Result:** verified on hardware. `ktool` flashes the UnitV (reset scheme `kd233`), and `x/devices/unitv/examples/hello` prints one line per second at 115200 (31 lines, mean period 0.9994 s, host-timed). Factory backup/restore was **dropped by the owner** mid-milestone; the board now runs `hello`. M1 also found a TinyGo 0.43 K210 timing bug (§4). Ticket [[ER-041-k210-flash-uart-hello|ER-041]]; M0: [[ER-K210-M0]].

**Paths moved in M3:** `hello` is now `drivers/unitv/examples/hello` (same binary hash, ER-K210-M3 (later commit) §1). The app UART question at the end is answered in ER-K210-M4 (later commit) §4 (115200 and 1.5 Mbaud work on this FT232BM).

**Owner, 2026-11-09 (during M1, verbatim):** "i don't care about existing ai camera image 🙂 i care about camera and kpu work only." The first 16 MB read was running at 115200 (≈ 11 KiB/s, 900 KiB read); I cancelled it and deleted the partial dump. No backup exists; no restore was done.

## 2. Flashing path (observed)

Tool: loboris/ktool at commit `0345aa90d9b3830641373fb4e3ce4edf45d0a46f` (2020-02-22), `ktool.py` SHA-256 `800794f7d621f44e393400d31b291c2f087d0cabf986dd35ae727eb33729dca5`, in `tmp/k210/ktool/`; Python 3.13.13 uv venv `tmp/k210/.venv` with pyserial 3.5. Reviewed before running: no network code; the only subprocess is `tput cols/lines`.

**Working command** (flash at 0 with ktool's SHA prefix, then reboot):

```
tmp/k210/.venv/bin/python tmp/k210/ktool/ktool.py -p /dev/cu.usbserial-6D52BBCC47 -B kd233 -b 115200 --noansi -a 0 <prog>.bin
→ Flash ID: 0xEF6018, unique ID: D4688020931C172C, size: 16 MB
→ Flashed 5973 B [2 chunks of 4096B] (00000000~00001FFF) in 0.858s
```

| Try | Result |
|---|---|
| `-B dan` (Maix Dock scheme) | `Greeting fail … SLIP receive timeout (wait frame start)` |
| no `-B` (auto-detect) | same: ktool raises a plain `Exception` on receive timeout but auto-detect only catches its own `TimeoutError` (`ktool.py:776` vs `:1590`), so it never tries the second scheme |
| `-B kd233` | ROM ISP detected, 2nd-stage ISP loaded in 0.93 s → **works** |
| read at `-b 1500000` | 2nd stage ok, then `Response error: wrong size (43406)` after 256 KiB (host read loop drops bytes) |
| `-b 1000000`, `-b 921600` | baud switch fails: `Unexcepted Error, retrying… Attempting to use a port that is not open` |
| read at `-b 115200` | worked, ≈ 11 KiB/s (cancelled per owner) |

Gotcha for any future dump: `read_flash` logs a CRC mismatch but **keeps the bad chunk** (`sys.exit(2)` commented out, `ktool.py:1321–1323`), so one read proves nothing; two reads with equal SHA-256 do.

Board reset for capture: `capture.py` opens the port with DTR and RTS deasserted, then pulses RTS; the board boots from flash. ~6 KB programs flash in under 1 s at 115200, so no faster ISP baud is needed for development.

## 4. Finding: every second `time.Sleep` returns at once (TinyGo 0.43, K210)

The first M0 `hello` (`write; time.Sleep(time.Second)` in a loop) printed **two lines per second**: lines arrive in pairs, 1.000 s apart (host timestamps `…456.964 0`, `…457.961 1`, `…457.961 2`, `…458.965 3`, `…458.971 4`; 21 lines in 10 s, reproduced after a reflash).

Probes (source `tmp/k210/probes/sleepprobe/main.go`, logs `tmp/k210/logs/sleepprobe*.log`):

| Probe | Result |
|---|---|
| `t0 := time.Now(); time.Sleep(100ms); print(time.Since(t0))` | 100000 µs every time |
| same with 1 s | 1000000 µs every time, 6 lines in 7 s |
| hello's loop + `time.Now()` before each Sleep | 1000001 µs, one line per second |

So the CLINT clock and `sleepTicks` are right; the early return appears only when nothing reads the clock between Sleeps. Root cause **not found** (it sits in the runtime: `scheduler_cooperative.go` sleep queue and/or `runtime_k210.go` `sleepTicks`). Fix in EasyRobot: `hello` sleeps to a deadline, `for d := time.Until(next); d > 0; d = time.Until(next) { time.Sleep(d) }`, which is correct whether or not Sleep returns early. **Risk for M3/M4:** sensor reset and power-up delays written as bare `time.Sleep` may be too short; camera code uses deadline sleeps until the bug is understood.
