## 2. Sensor id on the board (observed)

`drivers/unitv/examples/camid` (9,232 B) flashed with ktool (`-B kd233`, M1), log `tmp/k210/logs/camid-1.log`, one line per second:

```
camid pll0=780000000 aclk=390000000 apb1=195000000 xclk=24375000 sccb=382352 sensor=OV2640 addr=0x30 pid=0x26 ver=0x42
```

- **Camera pins:** the Sipeed/MaixPy K210 mapping worked first time: SCCB SDA IO40, SCL IO41, RST IO42, VSYNC IO43, PWDN IO44, HREF IO45, XCLK IO46, PCLK IO47 (`unitv.CameraPins`). No network fetch of M5's board config was needed.
- **Clocks (read from SYSCTL, not assumed):** PLL0 780 MHz, CPU/ACLK 390 MHz (matches TinyGo's fixed 390 MHz), APB1 195 MHz. XCLK 24.375 MHz (divider from APB1). SCCB runs at 382 kHz: with APB1 at 195 MHz the 8-bit SCL counters bottom out there (OV2640 allows 400 kHz).
- **Variant:** OV2640, not the OV7740 the plan expected for U078-C. The ideation plan's "OV7740 77 42" example no longer applies.

## 3. Camera API as implemented (contract for esp32cam)

Changes from the M0 draft are marked ▲.

```go
// package sensor (no build tag) — drivers/camera/sensor
type Format uint8                         // Y8, RGB565, YUV422, JPEG
type Resolution struct{ W, H uint16 }     // QQVGA, QVGA, VGA
type Mode struct { Resolution; Format Format }
type Bus interface {                       // ▲ 7-bit device address per call; 8- and 16-bit registers
	ReadReg8(dev, reg uint8) (uint8, error)
	WriteReg8(dev, reg, val uint8) error
	ReadReg16(dev uint8, reg uint16) (uint8, error)   // OV3660/OV5640
	WriteReg16(dev uint8, reg uint16, val uint8) error
}
type Sensor interface { Name() string; Init(Mode) error }   // ▲ driver holds its Bus
type Model uint8                           // Unknown, OV7740, OV2640, OV3660, OV5640 (= frame sensor ids)
type ID struct { Model Model; Addr, PID, VER uint8 }
func Identify(Bus) (ID, error)             // ▲ id read without configuring; ErrNotFound

// package ov2640 (no build tag) — drivers/camera/sensor/ov2640
type Options struct { ClockDouble bool; ClockDiv uint8; YUVLowByteFirst bool }  // host timing/bus quirks
type Sensor struct { Bus sensor.Bus; Opts Options }        // implements sensor.Sensor

// package camera — camera.go (no tag) + one backend file per host
type Config struct { sensor.Mode; XCLK uint32 }
type Frame struct { Width, Height uint16; Format sensor.Format; Seq uint32; Data []byte }
func FrameSize(Config) int
var ErrTimeout, ErrBufSize, ErrNoDriver error
// per host (camera_k210.go now; camera_esp32s3.go later), identical names:
type Pins struct{ … }                       // ▲ host-specific pin set, provided by the board package
func Identify(cfg Config, pins Pins) (sensor.ID, error)    // ▲
func Open(cfg Config, pins Pins) (*Camera, error)          // ▲ pins argument
func (c *Camera) Sensor() sensor.ID                         // ▲ was string
func (c *Camera) Capture(buf []byte) (Frame, error)
func (c *Camera) Close() error
```

- **No stub files:** a host without a backend has no `Identify`/`Open`, so its firmware build fails at compile time. Host builds and tests cover `camera.go`, `sensor/…` and `frame/`.
- **Delays:** sensor drivers wait with a deadline loop against `time.Now`, not a bare `time.Sleep` (TinyGo 0.43 K210 sleep bug, [[ER-K210-M1]] §4).
- **Board pins:** the board package owns them (`unitv.CameraPins`); esp32cam's board package would define its own `camera.Pins` value.

## 4. Camera frame format v1 (canonical; shared with esp32cam)

Implemented in `drivers/camera/frame` (encoder for firmware, decoder for the host; stdlib only: `bufio`, `encoding/binary`, `errors`, `hash/crc32`, `io`) and `cmd/camframe`. The layout follows the W4 SPI chunk header ([[2026-11-09-k230-spi-w4]] §3) with its own magic and without DMA padding.

**Stream.** The device writes chunks to its UART. Anything between chunks (boot banners, `println`) is allowed: the receiver scans for the magic and passes other bytes through as text. One image = one `frame_seq` = `chunk_cnt` chunks.

```text
Chunk = Header (24 B) || Payload (payload_len B, no padding)

Header, little-endian:
  off  size  field
   0   u32   magic        0x4D495245, bytes on the wire "ERIM"
   4   u32   frame_seq    +1 per image; wraps
   8   u16   chunk_idx    0 .. chunk_cnt-1
  10   u16   chunk_cnt    ≥ 1
  12   u16   payload_len  1 .. 4096
  14   u16   flags        bit0 first, bit1 last, bit2 image meta present
  16   u32   frame_ts     device clock, µs, low 32 bits (capture start)
  20   u32   crc32        CRC-32/IEEE (hash/crc32.ChecksumIEEE) over header bytes 0..19, then the payload

Image meta, 16 B, at the start of the first chunk's payload (payload_len counts it):
   0   u16   width        pixels, ≥ 1
   2   u16   height       pixels, ≥ 1
   4   u8    format       1 Y8 · 2 RGB565 little-endian · 3 RGB565 big-endian · 4 YUYV · 5 JPEG · 6 RGB888 planar
   5   u8    version      1
   6   u16   stride       bytes per row; 0 = tight; RGB888 planar: all three planes (each plane row = stride/3); ignored for JPEG
   8   u32   data_len     image bytes over all chunks, meta excluded (JPEG: exact file length)
  12   u8    sensor       0 unknown · 1 OV7740 · 2 OV2640 · 3 OV3660 · 4 OV5640
  13   u8[3] reserved     0
```

**Receiver rules** (as implemented and tested):
- **Header checks:** find the magic; read 24 B; reject `payload_len` 0 or > 4096, `chunk_cnt` 0, `chunk_idx ≥ chunk_cnt`, or inconsistent flags (`first` and `meta` exactly on chunk 0 with ≥ 16 B payload, `last` exactly on the last chunk) and rescan from magic + 1. Unknown flag bits are ignored (additive).
- **CRC:** check the CRC; on a mismatch, drop the current image and rescan from magic + 1 (the skipped bytes count as text).
- **Ordering:** a missing, duplicate or out-of-order `chunk_idx`, or a new `frame_seq` before `last`, drops the image.
- **Meta:** a version byte other than 1, a zero dimension, a stride that is too small, odd YUYV width, or a data_len mismatch drops it. Unknown formats are delivered (additive); the encoder refuses them.
- **Completion:** an image completes when `last` arrives and the bytes equal `16 + data_len`.
- **Counters:** `Dropped` = images with ≥ 1 valid chunk that never completed, once per seq. `Lost` = `frame_seq` gaps between valid chunks (backwards jumps ≥ 2³¹, a device reboot, are not counted). The encoder advances `seq` even when a write fails, so the receiver sees a failed image as lost.
- **Versioning:** a breaking change gets a new magic; new formats, sensor ids and flag bits are additive in v1.

**Tool:** `go run ./cmd/camframe -port <dev> -baud <rate> -n <images> -out <dir> [-raw tee.bin] [-trigger c] [-timeout 30s]`, or `-in recorded.bin`. It writes `<dir>/<seq>.png` (Y8 grey; RGB565 LE/BE, YUYV (BT.601 full range) and planar converted to RGB; JPEG decoded with `image/jpeg`, raw `<seq>.jpg` kept). It prints device text as `dev| …` on stderr and ends with `images= saved= fps= crc_errors= dropped= lost= text_bytes=`. Serial: darwin (termios + IOSSIOSPEED) and linux (termios2/BOTHER), raw 8N1, DTR/RTS deasserted; other OSes get a clear error (file mode works everywhere). It writes to the port only `-trigger` bytes. Opening the port resets the UnitV on macOS (observed in M1 and here).

## 6. Sleep bug: minimal repro for an upstream issue

`tmp/k210/probes/sleeprepro/main.go`, stock `maixbit` target (no EasyRobot code): UARTHS configured, a `strconv`-formatted line written, then `time.Sleep(time.Second)`. It prints 17 lines in 8 s, in pairs 1.000 s apart (`logs/sleeprepro-maixbit.log`). Not reproduced (1.000 s period) by a `println`/Sleep loop, nor by the same loop writing a constant `[]byte("tick\r\n")`.

**Narrowing probe** (after verify's suggestion; `probes/sleepnarrow/main.go`, log `logs/sleepnarrow.log`, every line kept). It is the repro loop plus three raw CLINT register reads before each Sleep (`MTIMECMP[0]`, `MIP.MTIP`, `MTIME`; no runtime clock call) and one `MTIME` read after. Result: **no early return**. Every Sleep measured `d = 7,800,003–7,800,009` ticks (1.000 s at 7.8 MHz), and lines came 1 s apart. `MTIP` was pending (`mip=128`) before every Sleep after the first, ~20,350 ticks (2.6 ms) past the old compare.

So the early return is timing/layout-sensitive. A few instructions before the Sleep (these reads, or `time.Now()`) hide it. That points away from a stale-flag bug that should show regardless, and toward a race between the scheduler's sleep accounting and the timer interrupt [INFERENCE]. Root cause still open; filing upstream is a public network action: owner decision below.

**Why M3/M4 timing is safe anyway:** every delay in the camera code waits on a deadline checked against `time.Now`, so an early return just loops again. That covers the 200 ms PWDN/RESET steps (`dvp_k210.go` `sleep`), the 10 µs DVP reset, the OV2640 soft-reset and format/window settles (`ov2640.go` `sleep`), and the SCCB/DVP polling timeouts (`time.Now().After(end)`). No bare `time.Sleep` remains in a timing path under `drivers/` (the `frame` example's retry-open pause is not a timing path).
