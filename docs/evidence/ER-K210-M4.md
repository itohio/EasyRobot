# ER-K210 M4 — a camera image of the room, fetched over UART

**Result:** verified on hardware; meets the owner's acceptance. The UnitV (OV2640) captured QVGA RGB565 and QVGA Y8 images of the room. They were streamed in camera frame format v1 ([[ER-K210-M3]] §4) at 1.5 Mbaud, and `cmd/camframe` on the Mac decoded and CRC-checked them and wrote the PNGs below. The link loses bytes in about 1% of chunks even with pacing; the format drops those images and keeps going (§4). Uncommitted; no commit before Leader's go. Ticket [[ER-044-k210-frame-over-uart|ER-044]].

## 3. What it took (findings, observed)

| # | Symptom | Cause / fix | Evidence |
|---|---|---|---|
| 1 | Every pixel 0 (frames complete, buffer overwritten with zeros; OV2640 colour bar too) | the DVP's 8 data inputs are the SPI0 D0–D7 pins and must be routed: `SYSCTL.MISC.SPI_DVP_DATA_ENABLE` (SDK `sysctl_set_spi0_dvp_data`). Set in `dvpInit` | diag before: `zeros=38400`; after: `zeros=423 sum=3875252`. `POWER_SEL=0x00000000` (all IO banks 3.3 V), `MISC=0x00000100` before the fix |
| 2 | RGB565 image right but edges jagged | the DVP display output stores each pixel pair with the two 16-bit pixels swapped in the 32-bit word; `Capture` swaps the halves in place, so `Frame.Data` is plain RGB565 little-endian | host re-decode of one raw frame as LE, BE, halfword-swapped LE/BE: only halfword-swapped LE is clean |
| 3 | Y8 noise-like (DVP `FORMAT_Y`) or striped (`FORMAT_YUV`, R plane) | OV2640 must send YUV with `IMAGE_MODE.LBYTE_FIRST`; then the DVP's Y mode writes clean luma to the AI R plane. `ov2640.Options.YUVLowByteFirst` (K210 backend sets it; ESP32 leaves it off) | images `tmp/k210/img/y8`, `img/y8b` |
| 4 | CPU must not read DVP frames through the cache | `Capture` returns the buffer's uncached alias (`addr − 0x4000_0000`); a check comparing CRC-32 of `Frame.Data` before and after sending saw no change | `DATA CHANGED` never printed (25 s run) |
| 5 | Bytes lost on the link | below | §4 |

DVP setup follows the Kendryte standalone SDK `dvp.c` sequence: burst 4 beats, `HREF_BURST_NUM = width/32`, `LINE_NUM = height`, auto mode off, frames polled via `STS` (start → `DVP_EN` → finish). It is not interrupt-driven yet; M7 will need IRQ 24 for overlap.

## 4. The UART link

The UnitV's USB-serial chip is an **FTDI FT232BM** (`bcdDevice 0x0400`, VID:PID 0403:6001, "M5Stack Intf"), on macOS's built-in driver. Observed:

- **Usable rates:**
  - Clean: **115200** and **1,500,000** (K210 divider exact at both).
  - Garbage: host 460800, 921600 and 1,000,000, from pyserial and from camframe (IOSSIOSPEED), with the device at the same rate (`logs/baud921600.raw`, `rgb-qvga-460k.raw`, `rgb-qvga-1m.raw`).
  - `baudscan.py` (device cycling rates) saw clean text only at 115200 and 1.5 M.
- **Loss at 1.5 Mbaud:** corrupt chunks are *short* (5–130 bytes missing before the next magic), i.e. lost bytes, not flipped bits. That fits the FT232BM's 384-byte receive buffer overflowing while the host is slow to poll [INFERENCE].

| Run (QVGA RGB565, 1.5 Mbaud) | Chunks ok / bad | Bytes/s |
|---|---|---|
| unpaced, camframe (45 s) | 1279 / 70 | — |
| unpaced, Python tight read loop (20 s) | 603 / 40 | 130,870 |
| paced 512 B / 2 ms (20 s) | 400 / 10 | 83,555 |
| paced 256 B / 2 ms (30 s) — default | 467 / 5 | 64,032 |

Consequences:
- At ~1% chunk loss a 38-chunk QVGA RGB565 image arrives whole about 2 times in 3, and a 19-chunk Y8 image about 5 times in 6. The format detects every loss: CRC, dropped/lost counters.
- M7's "CRC-clean for 10 min" is not reachable on this link as is. Options: smaller images (QQVGA Y8 is 5 chunks); a host-side reader that never stalls (camframe already only reads + decodes); Grove UART to an ESP32 instead of USB; or a trigger/ack resend.

## 5. Code (new, uncommitted)

- `drivers/camera/sensor/ov2640/ov2640.go` — init/window/format tables from espressif/esp32-camera v2.1.9 `ov2640_settings.h` (Apache-2.0, local sparse clone `~/src/docs/research/esp32-camera`, `b3f7fe8`); register names from OpenMV `ov2640_regs.h` (MIT); window/clock sequence reconstructed from esp32-camera `ov2640.c` (not in the local clone — written from memory, validated by these images). CIF-class modes up to 400×296; Y8/RGB565/YUV422/JPEG. Tests: output size registers (ZMOW/ZMOH/ZMHH), IMAGE_MODE per format and option, CLKRC, soft reset first, DSP not left bypassed, rejected modes.
- `drivers/camera/dvp_k210.go` — `dvpConfigure`, `dvpCaptureOne`, data-path enable.
- `drivers/camera/camera_k210.go` — `Open` (identify → OV2640 driver → DVP config), `Capture` (uncached alias, halfword fix), `Close`, `ErrFormat` (K210: Y8 and RGB565; widths multiple of 32).
- `drivers/unitv/examples/frame/main.go` — capture → `frame.Encoder` → paced UART writer; 10 warm-up frames for auto exposure.
- Scratch (not in the repo): `tmp/k210/{flash.sh,rawcap.py,baudscan.py,probes/baud}`; the temporary `drivers/unitv/examples/dvpdiag` was deleted after use.

- Why the host cannot use 460800–1,000,000 on this FT232BM/macOS pair. Linux host untested.
- Interrupt-driven capture and double buffering (M7).
