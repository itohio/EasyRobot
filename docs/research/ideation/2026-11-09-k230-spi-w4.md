## Verdict

- **K230:** prototype on **CanMV (MicroPython)**. It has camera, KPU and an SPI master in one image. Production code goes to the Linux SDK in C/C++. Go on `linux/riscv64` can't call the KPU without CGo, so keep Go for CPU-side tools.
- **Backbone:** the KPU has headroom for any small backbone (MobileNetV2 ≥ 670 fps per the product brief). Choose by **SPI bytes**, not compute: a 10×10×256 or 7×7×320 int8 map.
- **ESP32 side:** use an **ESP32-S3** as the SPI slave. The driver supports up to **60 MHz**, DMA lengths must be multiples of 4, and a ready GPIO is recommended.
  - **TinyGo:** on the original **ESP32** (esp32-coreboard-v2 docs) `machine.SPI` is controller-only at ≤ 40 MHz. On the **ESP32-S3**, TinyGo now implements SPI: CHANGELOG "esp32s3: implement SPI (#5169)", reported. The xiao-esp32s3 `machine` reference shows a controller API (`Configure`, `Transfer`, `Tx`), `SPI0` = `esp.SPI2` and `SPI1` = `esp.SPI3`, a default of 80 MHz, and no target/slave field in `SPIConfig` (observed). S3 slave mode is therefore most likely absent, `#verify` against TinyGo's `machine_esp32s3_spi` source. A TinyGo slave probably still needs register-level code; an ESP-IDF C recorder is the fast path.
- **Framing:** fixed 4 KB chunks with a 24-byte header and CRC-32, plus a READY line for back-pressure. A frame is dropped whole when the ESP32 isn't ready, which matches dndm's `latest` semantics.
- **SD recording:** one ESP-IDF benchmark run (one 64 GB SDXC card, SDMMC 4-bit at 40 MHz, probably an original ESP32, not an S3):
  - 64 KB writes: 10–12.7 MB/s;
  - **new-file** writes of other sizes (53/77 KB): 7.5–7.9 MB/s;
  - ~0.5 MB/s only for non-cluster writes into an **existing** file and for 0.25 KB writes.

  The 0.63 MB/s budget fits with ~12–16× margin. Writing aligned 64 KB blocks into pre-allocated files stays the recommended rule.

## 2. ESP32 SPI slave

| Fact | Source |
|---|---|
| ESP32-S3 SPI slaves "are designed to operate at up to 60 MHz"; 50 % duty cycle required | reported, ESP-IDF v5.3.2 SPI slave docs |
| Transactions > 64 B need DMA; the RX buffer must be word-aligned, and the host should write lengths that are multiples of 4 bytes, or the data is discarded | same |
| "All transactions must be handled by the CPU … noticeable latency"; queueing (`spi_slave_queue_trans` + `get_trans_result`) doubles the response rate; a handshake GPIO is recommended | same |
| ≤ 80 MHz: GPIO matrix routing behaves like IO_MUX; SPI2 IO_MUX pins: CS0 10, SCLK 12, MISO 13, MOSI 11 | same |
| TinyGo **ESP32** (esp32-coreboard-v2) `machine.SPI`: `Configure` and `Transfer` only (controller); frequency "up to 40MHz" in 40 MHz / n steps; **no slave/target mode** (I²C has a target mode, SPI doesn't) | observed, tinygo.org `machine` reference (esp32-coreboard-v2) |
| TinyGo **ESP32-S3** (xiao-esp32s3) `machine.SPI`: `Configure`, `Transfer`, `Tx`; `SPI0` = `esp.SPI2` (FSPI), `SPI1` = `esp.SPI3`; `SPI_DEFAULT_FREQUENCY = 80e6` ("maximum safe speed"); `SPIConfig{Frequency, SCK, SDO, SDI, CS, LSBFirst, Mode}` with **no target-mode field**. CHANGELOG: "esp32s3: implement SPI (#5169)" | observed, tinygo.org `machine` reference (xiao-esp32s3); changelog entry reported. Slave support `#verify` in source |

**Capacity:**
- At 20 MHz the link moves 2.5 MB/s raw. With 4 KB transactions and per-transaction CPU latency, assume **≥ 1.5 MB/s** effective (`#verify`). That is above every single-map row of W4's table at 10 fps.
- The P3+P4+P5 set (179 KB/frame) at 10 fps needs 1.79 MB/s, so it requires ~30–40 MHz.

**TinyGo path** (inferred): TinyGo's S3 SPI API is controller-only (above). An SPI slave in TinyGo therefore means writing the GP-SPI slave and GDMA register sequences against `device/esp` register structs (`#verify` that nothing in the `machine_esp32s3` SPI source already does this). That is feasible but is new driver work, with interrupt handling. **Recommendation:** start the recorder in **ESP-IDF C** to validate the link and SD rates, then port the slave receive path to TinyGo if the TinyGo-only goal applies to the recorder too (owner decision 2).

## 3. SPI frame layout

**Design goals:**
- the ESP32 never parses protobuf on the hot path; it checks the CRC and appends (W4 proposal);
- DMA-friendly sizes (multiples of 4);
- loss of a chunk loses one frame, never the stream;
- a later dndm SPI face can reuse the same chunking, because faces delimit frames themselves (dndm link-context design).

```text
Transaction = Header(24 B) || Payload(≤ 4072 B, padded to a multiple of 4)

Header (little-endian):
  u32 magic      = 0x45524B34 ("4KRE")
  u32 frame_seq  — increments per feature frame
  u16 chunk_idx  — 0..chunk_cnt-1
  u16 chunk_cnt
  u16 payload_len   (unpadded)
  u16 flags      — bit0 first, bit1 last, bit2 frame-meta present
  u32 frame_ts   — K230 timestamp, µs (low 32 bits)
  u32 crc32      — CRC-32 (IEEE) over header bytes 0..19 and the unpadded payload
```

- **First chunk of each frame:** carries a fixed 32-byte frame meta in front of the tensor bytes. It holds shape (N, H, W, C as u16), dtype, layout (NHWC/NCHW), quantisation scale (f32) and zero point, the model id hash and the camera exposure. This is what W4 says `types.math.Tensor` lacks today.
- **Handshake:** the ESP32 drives **READY** high while at least 2 DMA buffers are queued. The K230 checks READY before each chunk.
  - If READY stays low for longer than one frame period, the K230 **drops the rest of the frame** and counts the drop. The next frame starts fresh.
  - This is `latest` delivery: no blocking and no unbounded queue.
- **Receiver rules:**
  - CRC failure → drop the frame;
  - missing `chunk_idx` → drop the frame;
  - `frame_seq` gaps → count lost frames.

  The recorder writes the **raw transactions** of complete frames, so the host decodes offline (W4 proposal).
- **Clock sync:** `frame_ts` is the K230 clock. Every 100 frames the ESP32 logs its own clock against `frame_seq`, and the host fits the offset and drift offline (inferred; avoids a sync protocol).

## 4. Sustained SD write rate

The ESP-IDF storage benchmark example output, from one SDMMC 4-bit card at 40 MHz in one run (64 GB SDXC). The target chip isn't named; a logged handle `0x3ffd8880` lies in the original ESP32's DRAM range, so it is probably an ESP32, not an S3 (inferred). Reported:

| Operation | Rate |
|---|---|
| raw write, 64 KB | 12.7 MB/s |
| raw write, 16–48 KB | 2.3–3.6 MB/s |
| FATFS write, 64 KB = cluster size (new file) | 10.0 MB/s |
| FATFS write, 64 KB into an existing file | 12.1 MB/s |
| FATFS write, 53 KB / 77 KB, **new file** | 7.5 / 7.9 MB/s |
| FATFS write, 53 KB / 77 KB into an **existing** file (`O_TRUNC`) | **~0.5 MB/s** (0.495 / 0.550) |
| FATFS write, 0.25 KB | ~0.53–0.58 MB/s |

**Rules for the recorder** (inferred from the table):
- format with 64 KB clusters;
- pre-allocate the file;
- buffer complete frames into **64 KB aligned blocks** (double-buffered in PSRAM or internal SRAM: 2 × 64 KB);
- `fsync` every N blocks, not every frame.

**Budget check:** 7×7×1280 int8 at 10 fps = 0.63 MB/s against ~10 MB/s for 64 KB new-file writes (~16×), or ~7.5 MB/s for misaligned new-file writes (~12×). 10×10×256 at 30 fps = 0.77 MB/s is fine as well. The rate to avoid is rewriting existing files in odd sizes; the recorder appends to pre-allocated files in 64 KB blocks. On an ESP32-S3, measure before relying on these numbers.

**TinyGo:** EasyRobot has no SD or FAT support (W4). TinyGo has no ESP32 SDMMC driver that I found (`#verify`). An SPI-mode SD card on the second GP-SPI (master) is slower than SDMMC; the margin still holds if it reaches ≥ 2 MB/s with 64 KB writes (`#verify`).

## Smallest offline experiment (EasyRobot, no hardware)

**`x/devices/spiframe`** (pure Go, host):
1. A `Chunker` that turns frame bytes plus meta into transactions, per §3.
2. An `Assembler` that rebuilds frames from a transaction stream.
3. A `Recorder` that packs complete frames into 64 KB aligned blocks written to an `io.WriterAt`.
4. A reader that replays blocks into frames.

Tests:
- round trip with random shapes;
- property tests with injected bit flips (CRC catches 100 %), dropped chunks (exactly that frame lost), duplicated or reordered chunks (rejected), and READY drops (the frame is skipped and later frames are intact);
- a 64 KB alignment assertion on every write.

Benchmark: host MB/s of `Assembler` + `Recorder`. The same code then runs on the ESP32 (TinyGo or a C port) with only the SPI DMA source swapped.
